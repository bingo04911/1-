# 实战方案：单台自有 VPS + 第三方订阅

对应配置：[`examples/single-origin.conf`](examples/single-origin.conf)

## 1. 你的真实拓扑

| 你以为的 | 实际的 |
| --- | --- |
| 3 条线路 | **2 个落地点** |
| 2 台搬瓦工 | **1 台机器、1 个 IP**，上面开了两个节点条目 |
| 中转平台 | **第三方完整代理服务**，出口在他们手里 |

**同一个 IP 上的两个节点条目不是两条线路。** 它们同生共死：
IP 被黑洞、机器宕机、机房故障，两个一起没。它们唯一的作用是
让这台机器多暴露一个可被主动探测的入口 —— 有代价，没收益。

**你自建侧的实际冗余度是 1。** 这是整套方案最薄弱的地方，
后面所有建议都围绕这一点。

## 2. 更正：证书判据不成立

上一轮我说「要求上传证书私钥 = 七层解密」，这个判据不完整，
**四层转发同样不需要证书**，所以「没要求上传」什么都证明不了。

真正的判据是：**那套节点的凭据是谁生成的。**

- 你把自己服务器的 IP、端口、密码填给平台，它给你一个入口 → 是中转，
  加密在你和自己的落地之间端到端完成，平台只搬运字节
- 平台直接给你一个订阅链接，你下载就能用，全程没填过自己的服务器
  → **这不是中转，是一套他们完整控制的代理服务**

你描述的是后者。

## 3. 那个平台到底能看到什么

说准确一点，避免过度恐慌，也避免低估：

**他们能看到：**

- 你的真实 IP、每次连接的时间、流量大小和模式
- **你访问的每一个目标域名 / IP** —— 代理协议本身必须携带目标地址，藏不掉
- 任何非 HTTPS 流量的明文内容

**他们看不到：**

- HTTPS 网站的**内容**。那一层加密是你的浏览器和网站之间端到端的，
  代理服务器只是转发密文。除非你在设备上主动信任了他们的根证书 ——
  正常使用不会发生，也永远不要这么做

另外提醒两点：**订阅链接本身就是你的身份标识**，别分享给别人；
而且客户端每次更新订阅都会把你的 IP 交给平台一次，即使你当时没在用它的节点。

结论：这个平台适合做速度层，跑普通浏览没问题。
但凡是你不希望被第三方记录访问记录的流量，应该走自己的线路 ——
配置文件的 `[Rule]` 里给了写法。

## 4. 唯一的关键改动：给搬瓦工挂 Cloudflare

只有一个 IP 的情况下，这件事比什么都重要，而且**免费**。

### 为什么单 IP 挂 CDN 仍然有效

很多人觉得"就一台机器，挂 CDN 也是同一个 IP，被墙照样死"。**这是错的。**

GFW 的 IP 黑洞是**方向性**的：它阻断的是「**从中国**到该 IP」这条路径。
而 Cloudflare 边缘节点回源到你服务器走的是境外链路，**根本不经过 GFW**。

所以源站 IP 被墙之后：

```
国内 → 搬瓦工 IP            ✗ 被黑洞阻断
国内 → CF anycast → 搬瓦工   ✓ 照常工作（后半段不经过 GFW）
```

同一台机器、同一个 IP，凭空多出一条在 IP 被墙后依然可用的通道。
这是单机用户成本最低、收益最大的一步。

**它不防的**：机器宕机、机房故障、供应商停机、CF 到国内被 QoS 限速。
这几种只有另一台机器能救。

### 部署步骤

1. **域名接入 Cloudflare**，加一条 `cdn.你的域名` 的 A 记录指向搬瓦工 IP，
   **代理状态必须是橙色小黄云**。灰色等于直连，白做。

2. **服务端装 nginx 或 caddy**，443 配 Let's Encrypt 真实证书，
   把一个随机路径反代到本地的 VMess WebSocket 端口。
   路径要随机，别用 `/ws`、`/vmess` 这种一猜就中的。

3. **防火墙只放行 Cloudflare IP 段到 443。漏了这一步前面全白做** ——
   否则别人扫全网 443 照样直接摸到你的源站，CDN 的隐藏效果归零：

   ```bash
   for ip in $(curl -s https://www.cloudflare.com/ips-v4); do
       ufw allow from "$ip" to any port 443 proto tcp
   done
   ufw deny 443/tcp
   ```

   直连入口用另一个端口（比如 8443），单独放行给所有来源。
   开了 IPv6 的话 `ips-v6` 也要一并处理。

4. **根路径挂个正常的静态网站**。有人直接访问域名时看到的应该是普通网站，
   不是 404 或 nginx 默认页。

5. **客户端**用 `examples/single-origin.conf`，把域名、UUID、路径换成你的。

## 5. 顺手做掉：合并那两个重复入口

那台机器上现在有两个节点条目。保留其一即可，另一个改成 CF 入口。
最终这台机器上应该正好两个入口，各司其职：

| 入口 | 端口 | 作用 | 失效条件 |
| --- | --- | --- | --- |
| 直连 | 8443 | 速度层，日常主力 | IP 被墙即失效 |
| CF | 443（仅 CF 段可达） | 生存层，保底 | 需 CF 整体失效 |

再多加协议入口不会增加冗余，只增加探测面。

## 6. IP 被墙后的处置流程

**Level 0（自动）** —— `Resilient` 降级链会自动切到 CF 入口。
你很可能只感觉到"变慢了一点"，而不是断网。**这就是挂 CF 的意义：
它把"立刻断网"变成"从容处理"。**

**Level 1** —— 确认是不是真的 IP 黑洞：境外测该 IP 的 443 正常、
国内全端口不通 → 是黑洞。只有某个端口不通 → 端口级封锁，换端口即可。

**Level 2** —— KiwiVM 面板换 IP。换完要改**两条** DNS 记录：
直连用的那条，以及 CF 那条的源站指向。别只改一条。

**Level 3** —— 换 IP 后还是不通（新 IP 可能还在同一个被针对的段里），
用面板的迁移数据中心功能，换段换线路更彻底。迁移前备份好配置和证书。

全程 CF 入口应该一直可用，所以你有时间慢慢弄，不用手忙脚乱。

## 7. 按性价比排序的下一步

1. **给搬瓦工挂 Cloudflare** —— 免费，半小时，收益最大。**先做这个**
2. **合并那两个重复入口** —— 5 分钟，纯减少暴露面
3. **加一台不同供应商的冷备机** —— 几美元/月。
   你自建侧冗余度是 1，这是唯一能补上的办法。
   同一家搬瓦工的第二台不算数：段级封锁和供应商侧问题会同时命中
4. **敏感流量不走第三方** —— 在 `[Rule]` 里把它们指到 `CDN` 组
5. 想要更强抗探测能力：装个支持 VLESS + REALITY 的客户端做独立第二通道，
   Surfboard 用不了 REALITY，见 [`anti-blocking.md`](anti-blocking.md) 第 7 节

## 8. 自查

```bash
python3 scripts/audit_surfboard_conf.py 你的配置.conf
```

审计脚本会检查是否存在 CDN 保底层、多个节点是否挤在同一主机上
（这正是你原来那两个搬瓦工条目的问题）、探测参数是否合理、
兜底是否错误地指向了 DIRECT。
