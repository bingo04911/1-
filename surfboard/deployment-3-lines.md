# 三线路改造方案：1 中转 + 2 台搬瓦工

对应配置：[`examples/3-lines.conf`](examples/3-lines.conf)

## 1. 现状的四个结构性问题

**问题一：两台搬瓦工不算两条独立线路。**
同一家供应商，很可能落在同一个机房、同一个 IP 段、同一条 CN2 回程上。
段级封锁、路由级干扰、供应商侧的策略变化都会同时命中两台。
你以为的「双保险」在最常见的失效场景下是单点。

**问题二：三条线全是直连 IP，死法完全一样。**
它们都靠「国内能连到某个境外 IP 的某个端口」工作。
一轮针对性封锁下来，三条可以在同一天全灭。
线路数量不等于冗余度 —— **冗余度取决于失效原因是否互不相关**。

**问题三：三条线全在日常使用，没有冷备。**
节点被封的最强相关因素就是「被使用」。全部线路都在跑流量，
意味着全部线路都在积累暴露。真出事时你没有任何一条干净的自救通道。

**问题四（需要你确认）：中转的落地指向哪里？**
如果中转平台的落地就是你那台搬瓦工，那你实际只有 **2 个落地点**，
中转和 BWH-A 会一起死。这种情况下「三条线」是账面数字。

## 2. 改造：把三条线重排成三层

核心思路不是加机器，是**让现有三条线的失效原因错开**。

| 线路 | 现在 | 改造后 | 失效原因 |
| --- | --- | --- | --- |
| 中转平台 | 日常主力 | 第一层主力 | 中转 IP 被封 / 平台跑路 |
| 搬瓦工 A | 直连备用 | 第一层备份 | 源站 IP 黑洞 |
| 搬瓦工 B | 直连备用 | **只走 Cloudflare，做保底层** | 需 CF 整体失效才会挂 |
| 搬瓦工 B 第二入口 | — | 冷备，平时零流量 | 未暴露，几乎不会被主动封 |

**唯一的关键改动是第三行**：把搬瓦工 B 的直连入口从客户端配置里彻底拿掉，
改成只经 Cloudflare 接入。

这么做之后：

- 客户端连的是 CF 的 anycast IP，**搬瓦工 B 的真实 IP 不再出现在任何客户端配置里**
- 国内探测不到它，扫不到它，因此它的存活率会显著高于另外两条
- 封锁 CF anycast IP 的附带损害极高（连带打死大量正常网站），不会被轻易针对
- 代价：速度不如 CN2 直连，且 CF 到国内的线路时快时慢。
  但它的职责是**保底**，不是主力 —— 主力全挂时能用就是胜利

## 3. 搬瓦工 B 挂 Cloudflare 的操作步骤

1. **域名接入 Cloudflare**，添加 `cdn.你的域名` 的 A 记录指向搬瓦工 B 的 IP，
   **代理状态必须是开启（小黄云橙色）**。灰色云等于直连，白做。

2. **服务端装 nginx 或 caddy**，443 端口配真实证书（Let's Encrypt），
   把某个随机路径反代到本地的 VMess WebSocket 端口。
   路径要随机，别用 `/ws`、`/vmess` 这类一猜就中的。

3. **防火墙只放行 Cloudflare 的 IP 段到 443**。这一步最关键，漏了前面全白做 ——
   否则别人扫全网 443 仍然能直接摸到你的源站，CDN 的隐藏效果归零：

   ```bash
   # 允许 Cloudflare 回源，拒绝其它所有来源访问 443
   for ip in $(curl -s https://www.cloudflare.com/ips-v4); do
       ufw allow from "$ip" to any port 443 proto tcp
   done
   ufw deny 443/tcp
   ```

   （用 iptables 或云防火墙同理。IPv6 段在 `ips-v6`，如果开了 IPv6 也要一并处理。）

4. **根路径挂一个正常的静态网站**。有人直接访问你的域名时，
   看到的应该是一个普通网站，而不是 404 或 nginx 默认页。

5. **客户端**用 `examples/3-lines.conf` 里的 `BWH-B-CDN`，
   把域名、UUID、路径换成你自己的。

CF 支持的 HTTPS 端口有 443 / 8443 / 2053 / 2083 / 2087 / 2096，
配置里已经放了一条 8443 的备用，主端口被干扰时自动降级，服务端不用改动。

## 4. 搬瓦工专项运维

**IP 被墙时的标准操作**，按顺序试：

1. **KiwiVM 面板换 IP** —— 最快。注意换到的新 IP 可能还在同一个段里，
   如果那个段整体被针对，换了也没用。免费额度和次数以面板显示为准。
2. **迁移数据中心** —— 面板里有迁移功能，会连带换一个新 IP，
   而且是完全不同的段和线路，比单纯换 IP 更彻底。有频率限制，别当日常操作用。
3. 迁移前先把配置和证书备份好，迁移过程机器会重建。

**两台机器必须放在不同机房。** 这是你现在最该做的一件事 ——
如果两台都在同一个 DC，趁现在把其中一台迁走。同机房的两台机器在
段级封锁面前是同一条线路。

**其它注意事项：**

- 搬瓦工对 BT / P2P 有明确限制，跑了可能直接停机 —— 这是丢机器不是丢 IP，代价更大
- 搬瓦工的 IP 段被扫得很厉害，SSH 务必改端口 + 禁用密码登录 + 只留密钥
- 同一台机器上不要开一堆协议入口，每多一个入口就多一个被探测面。
  搬瓦工 B 上的「CDN + 冷备」两个入口是经过权衡的例外（见配置里的说明）

## 5. 关于中转平台，你需要确认两件事

**第一，它是四层转发还是七层解密？**

- 四层（TCP/UDP 端口转发、DNAT、gost 隧道）：中转方看不到你的明文，
  加密是你和落地之间端到端的，中转只是搬运字节
- 七层（中转终结 TLS 再转发）：**中转方能看到你的全部明文流量**

问服务商，或者自己验证：如果中转要求你把证书或私钥传给它，那必然是七层。

**第二，它的落地指向哪里？**
如果落地就是你的搬瓦工 A，那它和 BWH-A 是同一个落地点，会一起死，
你的「三条线」实际是两条。这种情况下应该把中转的落地改到另一台机器，
或者干脆把它当成 BWH-A 的加速通道而不是独立线路。

无论四层还是七层，中转方都能看到**你的真实 IP 和全部流量元数据**
（连接时间、流量大小、目标数量）。它速度最好，适合做主力，
但不该是你唯一信任的通道 —— 这也是保留自建线路的意义。

## 6. 改造后自查

```bash
python3 scripts/audit_surfboard_conf.py 你的配置.conf
```

改造完成后应该满足：

- 有 WebSocket + TLS 节点（CDN 保底层存在）
- 节点不全在同一个域名下
- 探测 URL 是境外地址、间隔 180s 以内
- `FINAL` 指向代理组而不是 DIRECT

## 7. 如果还想再稳一档

按性价比排序：

1. **把两台搬瓦工迁到不同机房**（免费，面板操作，收益最大）
2. **确认中转落地不与搬瓦工 A 重合**（免费，一次确认）
3. 加一条**不同供应商**的小机器做纯冷备（每月几美元，不同 ASN 才有意义）
4. 装一个支持 VLESS + REALITY 的客户端（sing-box 等）作为独立技术栈的第二通道 ——
   Surfboard 用不了 REALITY，详见 [`anti-blocking.md`](anti-blocking.md) 第 7 节
