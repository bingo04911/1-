# 抗封锁手册：节点被墙的识别、对抗与恢复

上一份文档解决的是「流量不被解密、不泄漏」。这一份解决的是另一个问题：
**节点被封之后你还能不能上网，以及怎么让被封这件事晚一点发生。**

先给结论：**没有任何配置能让节点永不被封。** 现实目标是两个——
降低被针对的概率，以及在被封后几分钟内恢复，而不是几天。
所有下面的设计都围绕这两点。

## 0. 先认清 Surfboard 的能力边界

Surfboard 用的是 Surge 配置格式，**不支持 VLESS，也不支持 REALITY**——
目前公认抗主动探测和抗指纹最强的方案，它用不了。

它能用的最强抗封组合是 **VMess / Trojan + WebSocket + TLS 走 CDN**。
这不是次优选择的自我安慰：CDN 方案在「抗 IP 封锁」这个维度上其实是最强的，
弱在流量指纹层面。如果你需要 REALITY，那需要换客户端（见文末第 7 节），
把它作为**第二条独立通道**，而不是替换 Surfboard。

## 1. 你会被怎么封

| 封锁方式 | 现象 | 对抗手段 | 配置里对应的部分 |
| --- | --- | --- | --- |
| **IP 黑洞** | 境外测试服务器一切正常，国内 ping/TCP 全超时。最常见 | 走 CDN（封它附带损害太大）、多 ASN 分散、随时能换 IP | `VMess-CDN` + `CDN` 保底层 |
| **IP:端口封锁** | 443 不通但 SSH 的 22 端口还能连 | 换端口；Hysteria2 端口跳跃 | CDN 备用端口、`port-hopping` |
| **SNI / 域名封锁** | 该域名的 TLS 握手被 RST，换个域名指向同一 IP 又能用 | 换域名；不要用已被墙或敏感的域名做 SNI | `sni=` 用你自己的普通域名 |
| **主动探测** | 建站后不久 IP 就进黑洞，且没有明显流量诱因 | 只用 AEAD 协议；服务端对非法请求回落到真实网站 | AEAD 加密要求 + 服务端回落 |
| **流量指纹 / TLS-in-TLS** | 逐步限速，或在敏感时期突然精准失效 | CDN 混入正常流量；减少特征暴露面 | CDN 层 |
| **QoS 限速** | 能连上但速度被压到几十 KB/s，尤其晚高峰和敏感时期 | 换协议（TCP↔UDP）、换端口、换线路 | 三层降级链自动切走 |

最后一行要单独说：**限速不等于被封**，但很多人误判成被封而去换 IP，白折腾。
判断方法见下一节。

## 2. 诊断：到底是被封了，还是别的问题

按顺序做，5 分钟内能定性：

**第一步 —— 确认服务端还活着。**
从境外测一次（第三方在线 TCP 端口检测，或你另一台境外机器）。
境外连不上说明是服务本身挂了，跟封锁无关，去看服务端日志。

**第二步 —— 区分 IP 封锁和端口封锁。**
从国内网络测同一 IP 的不同端口（比如 443 和你的 SSH 端口）：

- 全部不通 → IP 级黑洞
- 只有 443 不通，其它端口通 → 端口级封锁，换个端口通常立刻恢复

**第三步 —— 区分 IP 封锁和域名封锁。**
用 IP 直连（临时把节点地址改成裸 IP，`sni` 保持原域名）：

- IP 直连能通、用域名不通 → 域名/SNI 被针对，换域名即可，服务器不用动
- 都不通 → IP 的问题

**第四步 —— 区分封锁和 QoS 限速。**
连得上但慢，就是限速不是封锁。换到 CDN 层或换端口试试；
如果所有线路都慢，多半是敏感时期的普遍性干扰，等或者换协议类型（TCP↔UDP 互换）。

**第五步 —— 排除自己这边的问题。**
换运营商测（手机流量 vs 宽带）。只有一家运营商不通，那是本地路由或运营商级干扰，
不是全国性封锁，换 CDN 线路一般能绕过。

## 3. 被封之后的恢复剧本

按成本从低到高，逐级往下：

**Level 0（自动，0 秒）**
配置里的 `Resilient` 降级链已经处理了：主力层探测失败 → 自动落到 CDN 层。
你可能根本不会察觉。这就是三层架构存在的意义。

**Level 1（1 分钟）—— 换端口。**
如果确诊是端口级封锁，把节点端口改成 CDN 支持的另一个 HTTPS 端口
（8443 / 2053 / 2083 / 2087 / 2096），服务端不用动。

**Level 2（5 分钟）—— 换 IP。**
IP 进黑洞了。云厂商那边释放并重新申请一个弹性 IP，或者用快照在另一个可用区重建。
**注意**：新 IP 也可能是别人用脏的，最好先测一下再迁。
如果你用的是 CDN，这一步只需要在 CDN 后台改源站 IP，客户端零改动。

**Level 3（10 分钟）—— 换域名。**
SNI 被针对时。准备一个备用域名指向同一台机器，改 `sni=` 和 `ws-headers` 的 Host。
平时就该常备两个域名，事发时再去注册就太晚了。

**Level 4（最后手段）—— 启用冷备。**
前面全失效时，手动把策略切到 `ColdStandby`。用完之后，
这条线路就不再"冷"了，要尽快恢复主力并重建一条新的冷备。

## 4. 降低被封概率的日常习惯

这些比配置本身更影响存活时间：

**域名和证书**
- 用普通的、看起来无关的域名，别用带明显翻墙含义的名字
- 域名根路径最好真的挂一个正常网站（静态页也行）——被访问时它就是个正常站点
- 用 Let's Encrypt 真实证书，别自签

**服务端伪装**
- 配置非授权请求回落到那个真实网站，让主动探测看到的是一个普通 web 服务器
- 这是对抗主动探测最有效的一招，客户端配置替代不了

**别把鸡蛋放一个篮子**
- 主力和冷备必须不同 ASN、不同机房、不同域名注册商
- 同一 IP 上不要同时开多个协议入口——每多一个入口就多一个被探测面

**流量习惯**
- 国内流量走直连分流（配置里已做）。代理流量越少，特征越不显眼
- 别拿代理跑 BT、大规模扫描、爬虫——这类流量最容易触发关注
- 敏感时期（重要会议、周年日期）降低使用强度，**尤其不要在这期间新建节点**，
  那段时间新 IP 的存活率明显更低

**关于机场**
如果你用的是机场而不是自建：节点被封往往和你的行为无关——共享 IP 被其他用户
用脏了你一样连坐。这种情况下唯一有效的对策是**同时订阅两家不同的机场**，
并且至少自建一条 CDN 线路作为最终保底。把所有希望寄托在一家机场上，
它跑路或被大规模封锁时你就彻底断线了。

## 5. 协议选型对照

| 方案 | 抗 IP 封锁 | 抗主动探测 | 抗流量分析 | 速度 | Surfboard |
| --- | --- | --- | --- | --- | --- |
| VMess + WS + TLS + CDN | **高** | 中高 | 中 | 中 | 支持 |
| Trojan + TLS 直连 | 低 | 中高（需服务端回落） | 中 | 高 | 支持 |
| Hysteria2 | 中（端口跳跃缓解） | 中 | 低（UDP 特征明显，易被 QoS） | **弱网下最高** | 支持 |
| Shadowsocks 2022 | 低 | **高**（AEAD + 重放保护） | 中 | 高 | 支持 |
| VLESS + REALITY | 低 | **最高** | **最高** | 高 | **不支持** |

几点需要说清楚的：

- **"抗 IP 封锁低"不等于方案差**。Trojan 直连速度最好，只是 IP 一旦进黑洞就得换 IP。
  它适合做主力，不适合做唯一方案。
- **SS2022 没有 TLS 外衣**，它是完全随机的流量。抗主动探测很强，
  但"不像任何已知协议"本身在部分地区也是一种可被统计出来的特征。
- **CDN 方案的弱点是 TLS-in-TLS**。在 TLS 里再套一层 TLS，握手时序和包长模式
  与正常 HTTPS 有可测量的差异，学术界和工程上都已有识别方法。
  客户端配置解决不了这一点——这是选择 CDN 时要接受的已知代价。
  换来的是 IP 层几乎无法被针对性封锁。

## 6. 自查

```bash
python3 scripts/audit_surfboard_conf.py /path/to/your.conf
```

审计脚本除了检查加密安全，也会检查抗封锁结构：有没有 CDN 保底层、
节点是否全部集中在同一个域名下、故障转移探测间隔是否过长、
探测 URL 是不是错误地指向了国内地址。

## 7. 如果需要更强的抗探测能力

Surfboard 用不了 REALITY。真正需要的话，方案是**并存**而不是替换：

- 日常用 Surfboard（配置管理和分流规则更好用）
- 另装一个支持 VLESS + REALITY 的客户端（sing-box、v2rayNG 等）作为独立冷备通道
- 两条通道的服务器必须完全独立——不同机器、不同 IP、不同域名

这样即使 Surfboard 那一整套线路全部失效，你还有一条基于完全不同技术栈的通道。
双通道的价值不在于哪个更强，而在于它们的失效原因互不相关。
